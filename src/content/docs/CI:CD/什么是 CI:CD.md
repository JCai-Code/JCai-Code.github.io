---
title: 什么是 CI/CD
---
CI/CD，即持续集成/持续交付，是一种软件开发实践，它自动化了代码的构建、测试和部署过程。它是 DevOps 工具链的关键组成部分。

CI/CD 由两部分组成：

- **持续集成 (CI)**：开发人员尽可能频繁地将代码更改合并到中央代码库中。这种做法有助于降低测试成本，并减少发布到生产环境的缺陷数量。
- **持续交付或持续部署(CD)**：流程的下一步，代码更改将完全自动地进行测试和部署（有或没有人工审批步骤）。

CI/CD 有助于确保代码始终处于可发布状态，并尽快将新功能和错误修复交付给客户。

## CI/CD 为什么重要

CI/CD 之所以重要，是因为它能够自动化和简化软件开发生命周期，使团队能够更快、更可靠地交付高质量应用程序。其重要性的主要原因包括：

- 加速开发周期
- 提高代码质量
- 降低部署风险
- 增加团队协作和透明度
- 高效的资源利用

## 持续集成、持续交付和持续部署之间的区别

### 持续集成

在传统的软件开发流程中，多个开发人员各自编写代码，只有在版本发布的最后阶段才会整合各自的工作成果。这导致了许多缺陷和问题，这些问题只能在漫长的测试阶段之后才能被发现和解决。在所有问题都解决之前，软件无法发布。这损害了软件质量，也意味着团队通常每年只能发布一到两个新版本。

持续集成 (CI) 的设计初衷就是为了解决这个问题，并支持敏捷开发流程。CI 意味着开发人员对代码所做的任何更改都会立即集成到软件项目的主分支中。CI 系统会自动运行测试来发现质量问题，开发人员可以快速获得反馈并立即修复问题。开发人员通常会将代码提交到主分支，或者在生命周期较短的特性分支上进行开发，只有当一个特性与其他代码更改集成到主分支中时，它才被视为完成。

在 CI 流程中，构建服务器负责接收新的代码更改，使用多个工具运行自动化测试，将代码集成到主分支中，并生成构建——部署软件所需的新版本软件工件。

持续集成（CI）极大地提高了软件开发的质量和速度。团队可以创建更多对用户有价值的功能，许多组织现在每周、每天甚至一天多次发布软件。

### 持续交付

传统上，部署新软件版本是一项庞大、复杂且风险极高的任务。新版本经过测试后，运维团队需要将其部署到生产环境。根据软件规模的不同，部署可能需要数小时、数天甚至数周，需要详细的检查清单、大量的手动步骤以及专业技术。部署经常失败，需要开发人员提供变通方案或紧急援助。

这种传统方法存在很多问题——它给团队带来压力，给组织带来成本和风险，并且会导致生产环境中出现错误和停机。

持续交付（CD，也称为 CDel）旨在通过自动化解决这些问题。CD 方法允许团队一键打包软件并将其部署到生产环境。CD 的基本原则是，对软件项目的任何更改都可以立即部署到生产环境，无需任何特殊操作。

CI 系统整合新变更并创建新版本后，CD 系统会将新版本打包，部署到测试环境，自动评估其行为，然后推送到生产环境。最后一步可以手动审批，但将新版本部署到生产环境无需任何手动操作。

实施持续交付需要自动化整个软件开发生命周期，包括构建、测试、环境搭建和部署。所有工件都必须存放在源代码仓库中，并且需要一种自动化机制来创建和更新环境。

真正的持续交付流水线具有诸多优势。它使开发团队能够快速为客户交付价值，并创建真正敏捷的开发流程。

### 持续部署

持续部署 (CDep) 比持续交付更进一步。生产流水线中所有阶段的所有变更都会经过自动化测试，如果测试通过，则会立即部署到生产环境并向客户开放。

持续部署终结了发布日期，是加快客户反馈循环、减轻团队压力的绝佳方式。开发人员可以专注于软件构建，并在完成后几分钟内看到软件在生产环境中运行。

持续部署的实施可能很困难。它需要在流程的各个阶段实现无缝自动化，需要强大的自动化测试套件，以及“一切皆持续”的文化，以便能够检测和快速响应生产问题。

## CI/CD 与 DevOps 之间的联系

DevOps 旨在促进开发 (Dev) 团队和运维 (Ops) 团队之间更好的协作和沟通。它通常需要改变开发生命周期的各个方面，包括岗位职责、工具、最佳实践以及生命周期的自动化。

DevOps 通常涉及以下内容：

- 采用自动化、可编程基础设施部署和维护以及迭代软件开发。
- 建立跨职能团队，同时促进文化变革，以在这些以前各自独立的团队之间建立信任。

CI/CD 为 DevOps 团队的工作提供支持。它使团队能够在整个开发生命周期中实现自动化，并快速验证应用程序并将其交付给最终用户。其工作原理如下：

- 持续集成工具可以帮助初始化流程，确保开发人员无需手动操作即可在共享存储库中构建、测试和验证代码。
- 持续交付工具将这些自动化步骤扩展到生产测试和配置，以实现发布管理。
- 持续部署工具会自动调用测试、处理配置、部署、监控和回滚。

## CI/CD 流水线包含哪些阶段

### Source

创建源代码是 CI/CD 流水线的第一阶段。在此阶段，开发人员将需求转化为功能性算法、特性和行为。工具通常因项目、项目语言和其他变量而异。因此，没有统一的源代码创建流水线。

源代码创建流程可以包含以下内容：

- 编程框架，例如 Java、.NET、C# 或 Python。
- 支持项目所选编程语言的集成开发环境（IDE）。
- 代码检查工具，例如漏洞扫描器、基本错误检测工具以及验证是否符合编码标准的工具。
- 代码库和版本控制系统，例如 Git。

### Build

构建阶段包括从代码库拉取源代码，建立与库、依赖项和模块的链接，并将这些组件构建成可执行文件。它通常需要一些工具来生成执行日志，查找错误，并在构建完成后通知开发人员。

构建工具因编程语言而异。某些场景可能需要特定的构建工具，而其他场景则可以使用同一个集成开发环境 (IDE) 来完成源代码开发和构建阶段。构建阶段可能还会使用其他工具，将可执行文件转换为可部署或打包的执行环境，例如虚拟机 (VM) 或 Docker 容器。

### Test

在源代码创建阶段，代码会进行静态测试。构建完成后，代码将进入下一个 CI/CD 阶段，进行动态测试，包括：

- 基本功能或单元测试，有助于验证新功能是否按预期工作。
- 回归测试，有助于确保更改不会破坏先前运行正常的功能。

除了功能测试和回归测试之外，构建过程还会进行集成性测试、性能测试和用户验收测试。如果在测试阶段出现错误，系统会将测试结果反馈给开发人员进行分析和修复。由于构建过程需要进行大量测试，开发人员会采用自动化测试来最大限度地减少人为错误并提高效率。

### Deploy

构建版本通过测试阶段后，即可进行部署。部署构建版本主要有两种方式：

- **持续交付**，构建版本会发送给人工审核，审核通过后才能部署。例如，新版本会自动部署到测试环境，但上线生产环境则需要人工审核或合并请求。
- **持续部署**，该流水线会自动将构建版本部署到测试、预发布和生产环境，前提是它通过了所有相关的测试，无需人工审批。

典型的部署阶段会创建部署环境并将构建版本迁移到部署目标（例如服务器）。可以使用自动化工具中的脚本或工作流来自动执行这些步骤。大多数部署还会集成错误报告和工单系统，以便在部署后检测意外错误并向开发人员发出警报。

## CI/CD 的挑战和现代 CI/CD 流水线的优势

CI/CD 流水线成功的秘诀在于确保应用程序更新能够快速且自动化地执行。团队在采用 CI/CD 时通常会面临以下挑战：

- **发布流程中的手动步骤**，许多 CI/CD 流程仍然使用手动测试和部署步骤。这会导致延迟并影响生产计划。手动 CI/CD 流程还可能导致代码合并冲突，并增加客户等待补丁和更新的时间。
- **停机风险**，手动基础设施管理流程会给 DevOps 团队带来诸多麻烦，因为它会造成停机风险。例如，超出容量的意外流量高峰会导致停机，需要手动操作才能恢复应用程序。
- **资源利用效率低下**，应用程序通常以低效的方式部署在服务器上。这意味着企业需要为容量支付更多费用。随着应用程序的增加、扩展和缩减，高效利用可用硬件资源会变得困难。无论应用程序运行在云端还是本地，情况都是如此。

## CI/CD 和 Kubernetes

基于 Kubernetes 的现代 CI/CD 流水线可以解决上述三个问题，它减少了在 CI/CD 流水线中开发和部署应用程序所需的时间和精力。其高效的资源管理模型提高了硬件利用率，实现了管理流程的自动化，并减少了对客户造成负面影响的中断。

Kubernetes CI/CD 流水线的优势包括：

- **减少缺陷**，Kubernetes 能够实现一致的部署和测试环境，从而有助于减少因环境不一致而引入的缺陷。通过确保代码在开发、测试和生产环境中运行于完全相同的环境中，Kubernetes 最大限度地降低了生产环境中出现意外行为的可能性。

- **更快的产品迭代速度**，Kubernetes 可自动执行许多部署步骤，例如扩展、负载均衡和监控。这种自动化有助于简化 CI/CD 工作流程，从而加快代码变更的迭代速度，进而加速向客户发布新功能和更新。
- **可预测的部署**，Kubernetes 使用声明式配置文件，允许团队定义应用程序环境的预期状态。这有助于确保部署的一致性、可复现性和易于排查故障，从而使部署过程更可预测并减少停机时间。
- **部署和配置编排**，协调配置活动并简化部署。Kubernetes 负责硬件和存储资源配置、软件部署、可扩展性和健康监控，并且可以根据特定需求进行完全定制。
- **声明式结构**，用简洁易读的代码描述所需环境或应用程序的最终状态。这使得从停机和生产问题中更快地恢复、更好地控制扩展以及简化灾难恢复流程成为可能。

## CI 工具

常用的 CI 工具包括 Codefresh、Jenkins、CircleCI、GitLab CI。

### Codefresh

Codefresh 是一套全面的 GitOps 持续集成工具集，专为 Kubernetes 和现代应用程序而设计。它从底层构建，围绕 Argo Workflows 和 Argo Events 实现了灵活性和可扩展性。它汲取了开源工具集的精华，并提供诸多关键的企业级功能，例如统一的用户界面、用于全云管理的单一管理平台、经过安全验证的企业级运行时、端到端审计以及跨应用程序的单点登录。

### Jenkins

Jenkins 是一款开源自动化工具，提供多种插件来帮助开发、部署和交付软件。它是一个服务器，允许开发人员将任务分配到不同的机器上，并执行分布式测试和部署。Jenkins Pipeline 提供多个插件，以简化持续集成 (CI) 流水线的实现。

### CircleCI

CircleCI 是一款持续集成 (CI) 工具，支持多种容器系统、交付机制和版本控制系统，例如 GitHub。CircleCI 可以运行包含缓存、资源类和 Docker 层缓存的复杂流水线。您可以在云端和本地部署此工具。

### GitLab CI

GitLab CI 是一款开源的持续集成 (CI) 工具。它允许您使用 GitLab API 安装和设置托管在 GitLab 上的项目。GitLab CI 可以帮助您测试和构建项目，并部署构建版本。它还能指出需要改进的地方，并允许您使用保密发行版来保护项目数据。

## CD 工具

### Argo CD

Argo CD 是一款原生于 Kubernetes 的持续交付 (CD) 工具，专为 GitOps 优化。它将配置存储在 Git 仓库中，并自动将其应用到 Kubernetes 集群，从而轻松集成到现有工作流程中。Argo CD 可以检测配置偏差、监控应用程序健康状况，并回滚不必要的配置更改。它还支持蓝绿部署和金丝雀部署等渐进式交付策略。

###  Spinnaker

Spinnaker 是一个面向多云环境的开源持续交付 (CD) 平台。它提供流水线管理系统，并可与众多云服务提供商集成。Spinnaker 提供流水线构建器以实现发布自动化，并允许您将现有流水线保存为 JSON 文件以便重复使用。它支持 Kubernetes，并可与 Prometheus、Datadog 和 StackDriver 等工具集成。

### GitHub Actions

GitHub Actions 是 GitHub 推出的 CI/CD 工具，GitHub 是全球最受欢迎的软件项目托管和协作平台。GitHub Actions 允许开发者使用简单的 YAML 语法创建自定义工作流，直接从 GitHub 代码库实现自动化工作流程。

### Harness.io

Harness.io 是一个注重易用的 CI/CD 平台。它提供可视化界面，用于构建和管理部署流水线，并可自动化各种 CI/CD 流程，例如金丝雀部署和回滚决策。Harness.io 可实时自动验证部署，以便在问题影响最终用户之前检测并解决它们。

## 支持 CI/CD 流水线集成的工具

除了 CI/CD 平台之外，还有各种工具通过处理工件、功能标志、安全性、监控和测试来改进软件交付。一些常用的工具包括：

- Artifactory：一个通用的制品仓库管理器，支持多种包格式，包括 Docker、Maven 和 npm。它确保在 CI/CD 流水线中高效地存储、版本控制和分发构建制品。
- LaunchDarkly：一个功能管理平台，支持功能标记，可实现可控的发布。它支持金丝雀部署、A/B 测试和渐进式功能发布，以最大限度地降低风险。
- SonarQube：一款代码质量和安全工具，用于分析源代码中的错误、漏洞和可维护性问题。它与 CI/CD 流水线集成，可在部署前强制执行代码标准。
- HashiCorp Vault：一款密钥管理工具，可安全地存储和管理 API 密钥、密码和其他敏感信息。它可确保 CI/CD 流水线和已部署应用程序的安全访问控制。
- Snyk：一款安全扫描工具，可检测开源依赖项、容器镜像和基础设施即代码 (IaC) 中的漏洞。它与 CI/CD 工作流程集成，以便及早发现并修复安全风险。
- Prometheus：一款专为云原生环境设计的开源监控和告警工具。它与 CI/CD 工作流程集成，可提供系统健康状况和性能的实时指标和告警。
- Grafana：一款可视化工具，可与 Prometheus 和其他数据源配合使用，创建仪表板以监控 CI/CD 管道、应用程序性能和基础设施健康状况。
- ELK Stack（Elasticsearch、Logstash、Kibana）：一套日志记录和分析解决方案，用于收集、处理和可视化来自 CI/CD 流水线的日志数据。它有助于诊断构建失败、安全问题和系统异常。

## CI/CD 最佳实践

### 只需构建一次

避免多次构建同一源代码。如果您需要构建、打包或捆绑软件，只需执行一次此步骤，并将生成的二进制文件推进到流程的下一阶段即可。

大多数成功的持续集成 (CI) 实现都将构建过程作为 CI/CD 周期的第一步，以确保软件在干净的环境中打包。这可以消除人为错误，并降低遗漏构件或错误包含构件的风险。此外，所有生成的构件都必须进行版本控制并上传到 Git，以确保每次在流程中需要它们时，都能使用相同版本的构建版本。

### 经常发布

只有当软件达到发布标准并在类似生产环境的测试中完成验证后，才能进行商业发布。因此，最好增加一个步骤，将新版本部署到真实的预生产测试环境，或者与当前生产版本一起部署到生产环境本身。

以下是一些发布策略，可以帮助您以较低的风险将软件部署到测试环境和生产环境：

- **金丝雀部署**，先向部分用户发布新版本，测试他们的反馈，如果效果良好，再推广到更多用户。如果测试失败，则回滚并重复上述步骤。

- **蓝绿部署**，在两个完全相同的生产环境中运行软件的当前版本和新版本。初始阶段，当前版本上线运行，新版本处于闲置状态。然后，将流量从当前版本切换到包含新版本的环境。这样，您就可以在真实用户流量上测试新版本，如果出现问题，您可以立即回滚到当前稳定版本。
- **A/B 测试**，A/B 测试是一种用于测试应用程序功能（例如用户体验变更）的方法。它将两个或多个版本略有不同的应用程序并行提供给生产环境用户。团队观察用户与每个版本的交互情况，当某个版本被认为成功时，便将其推广到所有用户。

### 将 CI/CD 流水线作为部署到生产环境的唯一途径

构建可靠、快速且安全的 CI/CD 流水线可以增强您对构建质量的信心。即使因为小变更或者紧急变更要求绕过发布流程，都可能损害之前的努力。

### 每次发布前都要清理环境

为了最大限度地发挥测试流程的作用，每次部署前清理预生产环境是值得的。

通过使用容器来托管环境和运行测试，您可以利用声明式配置（例如 Kubernetes YAML 文件）编写脚本，轻松启动和销毁每个新部署的环境。在每次部署之前实例化新容器可确保一致性，并便于扩展环境以并行测试多个构建版本。

### 使用代码可视化工具

代码可视化工具能够帮助开发人员和团队理解代码库的结构和依赖关系，从而更轻松地驾驭复杂的系统并优化 CI/CD 流水线。将可视化融入 CI/CD 流程，有助于识别潜在的瓶颈、可能影响构建过程的依赖关系以及可以改进代码质量的方面。
